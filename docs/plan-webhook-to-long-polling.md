# План перехода с Webhook на Long Polling (MAX API)

На основе [документации MAX API](https://dev.max.ru/docs-api) и [метода GET /updates](https://dev.max.ru/docs-api/methods/GET/updates).

---

## Принятые решения (реализовано)

1. **Режим:** пустой `WEBHOOK_URL` = Long Polling. Отдельный флаг не вводим.
2. **Окружение:** Long Polling используется и для локальной разработки/тестов, и для production.
3. **Отписка от Webhook:** при старте в режиме Long Polling бот вызывает GET /subscriptions, затем для каждой подписки DELETE /subscriptions?url=… (MAX API). Ручная отписка в кабинете не обязательна.

---

## 1. Кратко о различиях

| Аспект | Webhook (текущее) | Long Polling (целевое) |
|--------|-------------------|-------------------------|
| Кто инициирует | MAX шлёт POST на наш URL | Мы периодически вызываем GET `/updates` |
| Требования | Публичный HTTPS, подписка в кабинете | Только токен, без подписки |
| Рекомендация MAX | Production | Разработка и тестирование |
| Лимит | 30 rps на platform-api.max.ru | тот же 30 rps |

**Важно:** при включённой подписке на Webhook метод GET `/updates` не отдаёт обновления. Нужно сначала отписать бота от Webhook (см. шаг 4).

---

## 2. API Long Polling (GET /updates)

- **URL:** `GET https://platform-api.max.ru/updates`
- **Авторизация:** заголовок `Authorization: <access_token>` (query-параметры не поддерживаются).
- **Параметры:**
  - `limit` (optional) — макс. число обновлений в ответе, 1–1000, по умолчанию 100.
  - `timeout` (optional) — таймаут long poll в секундах, 0–90, по умолчанию 30.
  - `marker` (optional) — указатель на следующее ожидаемое обновление; если не передан — отдаются все новые после последнего подтверждения.
  - `types` (optional) — фильтр типов, например `message_created`, `message_callback`.
- **Ответ:** JSON с полями:
  - `updates` — массив объектов `Update`;
  - `marker` — указатель на следующую страницу (передавать в следующий запрос).

Структура **Update** совпадает с тем, что приходит в Webhook: `update_type`, `timestamp`, `message`, `user_locale`. Обработку можно переиспользовать.

---

## 3. Что уже есть в проекте и что менять

- **Обработчики событий** в `internal/bot/service.go` уже есть и пригодны для Long Polling:
  - `handleMessageCreated(ctx, raw json.RawMessage)`
  - `handleBotStarted(ctx, raw []byte)`
- **Типы:** обрабатываются `message_created`, `bot_started`. Формат `message` в ответе GET `/updates` такой же, как в теле Webhook.
- **Менять нужно:**
  - способ **получения** обновлений (вместо HTTP-хендлера — цикл GET `/updates`);
  - конфигурацию и **запуск** (режим Webhook vs Long Polling);
  - при выборе Long Polling — **отписка от Webhook** (см. ниже).

---

## 4. Отписка от Webhook перед переходом на Long Polling

- В документации: [GET /subscriptions](https://dev.max.ru/docs-api/methods/GET/subscriptions) — возвращает список подписок (Webhook).
- Чтобы GET `/updates` начал отдавать события, бот **не должен** быть подписан на Webhook. Варианты:
  1. **Вручную в кабинете MAX:** Чат-боты → Интеграция → удалить/отключить Webhook.
  2. **Через API:** если в документации есть метод вида `DELETE /subscriptions` или `DELETE /subscriptions/{id}` — вызвать его при старте приложения в режиме Long Polling (точный URL уточнить в [документации методов](https://dev.max.ru/docs-api/methods)).

**Рекомендация:** в плане реализации заложить шаг «проверить в документации MAX точный метод отписки (DELETE subscription) и при необходимости вызывать его при старте в режиме Long Polling».

## 5. План реализации (по шагам)

### Шаг 1. Конфигурация режима

- Ввести способ выбора режима, например:
  - переменная окружения `USE_LONG_POLLING=true` или
  - считать режим Long Polling включённым, если `WEBHOOK_URL` пустой (и при этом явно не требовать Webhook для запуска).
- В `internal/config/config.go` добавить флаг/поле, например `UseLongPolling bool`, и заполнять его из env.

### Шаг 2. Модуль запросов к GET /updates

- В `internal/bot/` (или отдельный пакет `internal/bot/poller`) реализовать:
  - тип ответа: `updatesResponse struct { Updates []Update `json:"updates"`; Marker *int64 `json:"marker"` }`.
  - тип `Update` можно вынести в общий тип с тем, что сейчас разбирается в Webhook (те же поля `update_type`, `message`, `timestamp`, `user_locale`), чтобы не дублировать парсинг.
  - функцию запроса одного «тика» Long Polling:  
    `GET {ApiBaseURL}/updates?timeout=30&limit=100` (и при повторных вызовах добавлять `&marker={marker}` из предыдущего ответа).
  - использовать тот же `Authorization` и `ApiBaseURL`, что и для остальных вызовов MAX (из `config` / существующего клиента).

### Шаг 3. Цикл Long Polling в фоне

- В `internal/bot/service.go` в `Start(ctx)`:
  - если включён Long Polling — **не** регистрировать Webhook (регистрация сейчас, судя по коду, делается в кабинете MAX, не в коде; в коде только хендлер).
  - запустить горутину с циклом:
    1. вызвать GET `/updates` с текущим `marker` (при первом вызове без `marker`);
    2. при успешном ответе — для каждого элемента `updates` по `update_type` вызывать те же обработчики, что и для Webhook: `message_created` → `handleMessageCreated`, `bot_started` → `handleBotStarted`;
    3. обновить `marker` из ответа для следующего запроса;
    4. при ошибке (сеть, 5xx) — логировать, сделать короткую паузу (backoff) и повторить;
    5. цикл прерывать по `ctx.Done()`.
- Убедиться, что при завершении приложения горутина корректно останавливается.

### Шаг 4. Условная регистрация HTTP-маршрута Webhook

- В `internal/api/service.go` регистрировать `POST /webhook` только если режим **не** Long Polling (например, только если `cfg.UseLongPolling == false` или `WebhookURL != ""`). Это избежит лишнего открытого эндпоинта и путаницы при тестах.

### Шаг 5. Отписка от Webhook при старте (опционально, по документации)

- Если в документации MAX есть метод удаления подписки (например, DELETE по id из GET `/subscriptions`):
  - при старте в режиме Long Polling вызывать его, чтобы гарантированно не иметь активного Webhook.
- Если такого метода нет — явно описать в README, что перед использованием Long Polling нужно вручную отключить Webhook в кабинете MAX.

### Шаг 6. Документация и окружение

- Обновить README:
  - описать режим Long Polling: переменные окружения, что Webhook в кабинете должен быть отключён.
  - оставить раздел про Webhook для production.
- В `.env.example` добавить, например, `USE_LONG_POLLING=false` (или пояснить, что пустой `WEBHOOK_URL` включает Long Polling).

### Шаг 7. (Опционально) Сохранение marker

- По умолчанию можно не сохранять `marker` между перезапусками: без `marker` API отдаёт «все новые» обновления, что приемлемо для разработки/тестов.
- Если понадобится минимизировать потерю событий при рестарте — сохранять последний `marker` (например, в файл или БД) и при старте передавать его в первый запрос GET `/updates`.

## 6. Риски и ограничения

- **Документация:** рекомендация MAX — Long Polling для разработки/тестирования, Webhook — для production. При переходе на Long Polling в проде возможны задержки доставки и зависимость от стабильности исходящих запросов с нашего сервера.
- **Лимит 30 rps:** при Long Polling один долгий запрос с `timeout=30` занимает один «слот» до ответа; при одном потоке опроса лимит вряд ли будет достигнут, но при нескольких инстансах или параллельных вызовах — учитывать.
- **Текущий код:** в `WebhookHandler` поле `webhookSecret` объявлено в структуре бота, но нигде не присваивается из `cfg.WebhookSecret` и не проверяется (заголовок `X-Webhook-Secret` не валидируется). Имеет смысл либо добавить проверку для режима Webhook, либо явно задокументировать, что проверка отключена.
