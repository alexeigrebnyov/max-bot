## 1. Фокус на сообщении при переходе из раздела "Сообщения"

### Проблема
При клике на сообщение в разделе `/messages` открывался чат, но пользователь не видел конкретное сообщение, на которое кликнул.

### Решение

#### Frontend (messages.html):
- **Добавлен `data-mid` атрибут** к каждому элементу `.message-group`
- **Обновлена функция `openChat()`** - теперь принимает параметр `mid` и передаёт его в URL
- **URL формат**: `/admin?chat_id=123&message_mid=abc`

#### Frontend (index.html):
- **Добавлен `data-mid` атрибут** к каждому сообщению в функции `renderMessages()`
- **Создана функция `scrollToMessage(mid)`**:
  - Находит сообщение по атрибуту `data-mid`
  - Плавно скроллит к нему (`scrollIntoView`)
  - Подсвечивает сообщение на 2 секунды
- **CSS анимация `highlight-pulse`** - желтая подсветка с тенью
- **Чтение параметра `message_mid`** из URL при загрузке страницы
- **Автоматический вызов** `scrollToMessage()` через 500ms после открытия чата

### Файлы:
```
web/static/messages.html    - добавлен data-mid и передача mid в URL
web/static/index.html        - скролл, подсветка, CSS анимация
```

## 2. Обновление контактов через EventSource

### Проблема
Список контактов обновлялся каждые 5 секунд через `setInterval(loadContacts, 5000)`, что вызывало мелькание интерфейса и лишние запросы к серверу.

### Решение

#### Backend (internal/bot/service.go):
- **Добавлен канал `NewContacts chan *tables.Contact`** в структуру `Service`
- **Инициализация канала** в `NewService()` с буфером 100
- **Создана функция `notifyContactUpdate(contact)`**:
  - Отправляет контакт в канал `NewContacts`
  - Защита от переполнения канала (non-blocking send)
  - Логирование успешной отправки и переполнения
- **Добавлены вызовы `notifyContactUpdate()`** во всех местах сохранения контактов:
  - `handleAwaitingPhoneEMCHash()` - после авторизации по EMC
  - `handleAwaitingBirthdate()` - после авторизации по дате рождения
  - `saveContact()` - при сохранении контакта по телефону
  - `saveContactByEMCHash()` - при создании/обновлении контакта по EMC hash

#### Backend (internal/api/handlers/evnts.go):
- **Добавлен импорт** `internal/storage/tables`
- **Добавлено поле `newContacts chan *tables.Contact`** в структуру `EventBroker`
- **Инициализация канала** в `NewEventBroker()`
- **Создана функция `broadcastContactsLoop()`**:
  - Читает из канала `NewContacts`
  - Оборачивает контакт в JSON с `type: "contact_update"`
  - Отправляет через `broadcast()`
- **Переименована `broadcastLoop()` в `broadcastMessagesLoop()`**:
  - Оборачивает сообщение в JSON с `type: "message"`
- **Создана общая функция `broadcast(data)`**:
  - Отправляет данные всем подключенным клиентам
  - Удаляет клиентов, которые не успевают читать

#### Frontend (index.html):
- **Обновлен обработчик `eventSource.onmessage`**:
  - Парсит JSON с полем `type`
  - Вызывает `handleMessageEvent()` для `type: "message"`
  - Вызывает `handleContactUpdateEvent()` для `type: "contact_update"`
  - Обратная совместимость для событий без `type`
- **Создана функция `handleMessageEvent(msg)`**:
  - Перенесена логика обработки сообщений из `onmessage`
  - Добавлен `data-mid` атрибут к создаваемым сообщениям
- **Создана функция `handleContactUpdateEvent(contact)`**:
  - Обновляет контакт в `contactsMap`
  - Находит элемент контакта по `data-chat-id`
  - Обновляет имя и аватар без перезагрузки всего списка
  - Если контакт новый - вызывает `loadContacts()`
- **Удалён `setInterval(loadContacts, 5000)`** - больше не нужен

### Формат событий SSE:

**Сообщение:**
```json
{
  "type": "message",
  "data": {
    "recipient": { "chat_id": 123, ... },
    "body": { "mid": "abc", "text": "Hello" },

    "timestamp": 1234567890
  }
}
```

**Обновление контакта:**
```json

  "type": "contact_update",
  "data": {
    "UserID": 456,
    "ChatID": 123,
    "Phone": "+79001234567",
    "Name": "John Doe",
    "EMC": "AB",
    "AvatarURL": "https://...",

  }
}
```

## 3. Исправление ошибки SQLITE_BUSY

### Проблема
При авторизации нового контакта возникала ошибка `database is locked (5) (SQLITE_BUSY)`. Это происходило из-за конкурентных запросов к SQLite:
- Сохранение контакта в БД
- Отправка события в EventSource
- Одновременный запрос `GetUnreadCount` от frontend

### Решение

#### Backend (internal/storage/service.go):
- **Включён WAL mode** (`PRAGMA journal_mode=WAL`):
  - Позволяет читать БД во время записи
  - Значительно улучшает конкурентность
- **Установлен busy_timeout** (`PRAGMA busy_timeout=5000`):
  - БД ждёт до 5 секунд вместо немедленной ошибки
  - Даёт время другим транзакциям завершиться
- **Настроен connection pool**:
  - `SetMaxOpenConns(1)` - SQLite поддерживает только одно соединение для записи
  - `SetMaxIdleConns(1)` - оптимизация использования ресурсов

### Код:
```go
// Настройка SQLite для лучшей конкурентности
db.SetMaxOpenConns(1)
db.SetMaxIdleConns(1)

// Включаем WAL mode для лучшей конкурентности
if _, err := db.Exec("PRAGMA journal_mode=WAL"); err != nil {
    log.Printf("Warning: failed to enable WAL mode: %v", err)
}

// Увеличиваем таймаут для занятой БД
if _, err := db.Exec("PRAGMA busy_timeout=5000"); err != nil {
    log.Printf("Warning: failed to set busy_timeout: %v", err)
}
```

## 4. Исправление счётчика непрочитанных сообщений

### Проблема
Счётчик непрочитанных сообщений перестал работать для сообщений, отправленных пользователю. Проблема была в неправильной проверке отправителя сообщения.

### Причина
В функции `handleMessageEvent()` использовалась проверка:
```javascript
const isIncoming = msg.sender?.user_id !== 0;
```
Эта проверка некорректна, так как `user_id` может быть любым числом.

### Решение

#### Frontend (index.html):
- **Исправлена проверка отправителя**:
  - Используется поле `msg.sender.is_bot` из структуры `Sender`
  - Счётчик увеличивается только для сообщений от пользователей (не от бота)

### Код:
```javascript
// Если чат не открыт, увеличиваем счётчик непрочитанных
// Только для входящих сообщений (не от бота)
const isIncoming = msg.sender && !msg.sender.is_bot;
if (isIncoming) {
    loadUnreadCount(msgChatId);
}
```

## 5. Очистка URL после скролла к сообщению

### Проблема
После перехода из раздела "Сообщения" параметр `message_mid` оставался в URL. При обновлении страницы сообщение снова подсвечивалось.

### Решение

#### Frontend (index.html):
- **Очистка параметра из URL** после скролла:
  - Используется `window.history.replaceState()`
  - URL изменяется с `/admin?chat_id=123&message_mid=abc` на `/admin?chat_id=123`
  - При обновлении страницы подсветка не повторяется

### Код:
```javascript
setTimeout(() => {
    scrollToMessage(messageMidParam);
    // Очищаем message_mid из URL после скролла
    const newUrl = new URL(window.location);
    newUrl.searchParams.delete('message_mid');
    window.history.replaceState({}, '', newUrl);
}, 500);
```

## Технические детали

### Буферизация каналов:
- `NewMessages`: буфер 100 сообщений
- `NewContacts`: буфер 100 контактов
- При переполнении событие отбрасывается с логированием

### Обратная совместимость:
- Если EventSource отправляет событие без поля `type`, оно обрабатывается как сообщение
- Старые клиенты продолжат работать

### Производительность:
- Обновление контакта не перерисовывает весь список
- Только изменённые DOM элементы обновляются
- Новые контакты вызывают полную перезагрузку списка

---

## Известные ограничения

1. **Скролл к сообщению** работает только если сообщение уже загружено в DOM (нет пагинации)
2. **Новые контакты** вызывают полную перезагрузку списка (можно оптимизировать)
3. **Удаление контактов** пока не обрабатывается через EventSource
4. **WAL mode** создаёт дополнительные файлы `-wal` и `-shm` рядом с БД
